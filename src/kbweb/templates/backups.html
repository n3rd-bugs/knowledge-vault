⚠ What lives on this internet-facing box — read this

  • The rclone credential DOES live here. It is needed to upload, so a compromise of this box exposes it — the attacker could read/write your backup remote. Prefer a least-privilege service account scoped to one Drive folder.
  • The age PRIVATE key does NOT live here. Only the age public recipient is stored; encryption is one-way on this box. Keep the private key OFF this machine (a workstation / USB) — it is required only to restore.
  • A box compromise exposes only ENCRYPTED backups. Without the off-box private key the uploaded *.age ciphertext cannot be decrypted.

Backup settings

Generate an age keypair

Generates a fresh keypair, stores the public recipient here, and shows the private key once — it is never stored and never shown again. Save it off this box immediately; you need it only to restore.

rclone credential

Paste a Google service-account JSON or an rclone.conf remote block (starting with [remote]). Stored write-only, mode 0600 — it is never shown back to you. Replacing it overwrites the previous value.

Host-side checklist (the one irreducible manual step)

These run on the HOST, not here — the web cannot drive an OAuth browser flow or write outside its bind-mounts:

  1. If you are NOT using a service account, authorize rclone on the host once: 
    rclone config        # create the remote named above, complete the OAuth flow
rclone lsd <remote>:  # smoke-test the remote is reachable
    A service account pasted above needs no browser OAuth.
  2. Save the age private key OFF this box. After ‘generate keypair’, copy the shown AGE-SECRET-KEY-… to a safe place on a DIFFERENT machine (never commit it, never leave it here). Restore points restore_test.sh --offsite at it via KB_AGE_IDENTITY.
  3. Enable + verify. Tick “enable offsite push”, save, then run a backup on the host and confirm a *.age object lands on the remote: 
    make backup
rclone lsf <remote>: | grep '\.age$'
