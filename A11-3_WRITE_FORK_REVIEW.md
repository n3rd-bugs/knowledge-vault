# A11-3 Adversarial Design Review — Branch B web-write fork

<!-- Produced 2026-07-21 by a 6-dimension adversarial DESIGN review (Fable 5, 3-lens verify). READ-ONLY design review BEFORE any write code, per WEBUI_TIERED_ACCESS_PLAN §5 Phase 4. VERDICT: the fork as designed is UNSAFE — requires kbcore-chokepoint rework + fixes to live pre-existing holes. -->

## Verdict

The proposed design (a confined `views_write.py` importing `{ingest, supersede, link, promote, reject, dismiss}` with four-layer route gating) is **NOT safe to implement as specified**. Enforcing trust/authorization at the *route* layer is structurally insufficient — the guarantees must move into **kbcore chokepoints** so no surface (web, MCP, REST, future) can bypass them (Invariant 2). The review also surfaced **live pre-existing holes** in kbcore/MCP that any rw grantee could exploit today, independent of the web fork.

## Confirmed findings (26)

### [1] CRITICAL — must-fix-prerequisite — review.dismiss() has ZERO project/cap authorization — a /review/{qid}/resolve dismiss is an ungated cross-project write
**File:** `src/kbcore/review.py`  
**Attack:** A signed-in reviewer (or any principal that reaches the /review zone) POSTs /review/{qid}/resolve?action=dismiss iterating qid=1..N. dismiss() closes review rows whose items live in projects the principal cannot read or write (withheld/NDA projects), silently suppressing that knowledge from ever being reviewed. It also leaks a queue-id oracle: nonexistent qid → NotFound 'does not exist'; existing qid → success or InvalidOperation 'already resolved' (distinguishable).  
**Required mitigation:** Move the row walls INTO kbcore.review.dismiss so no caller (the new web route, review_auto.bulk_resolve at review_auto.py:157, or any future surface) can bypass them — matching where promote/reject already keep theirs. Concretely: (a) in the same transaction/lock, resolve the row with `SELECT rq.item_id, rq.resolved, i.project FROM review_queue rq LEFT JOIN items i ON i.id=rq.item_id WHERE rq.id=%s FOR UPDATE OF rq`; (b) missing row → NotFound("review queue row {id} does not exist"); (c) for a NON-owner: an item-less row (item_id IS NULL — the sentinel) raises that SAME byte-identical NotFound (sentinel dismissal stays owner-only); otherwise assert_readable(project, same NotFound message) BEFORE assert_writable(project) — the _queued_item_id ordering, since assert_writable's message embeds the project name; (d) ORDER MATTERS on the resolved-state check: for a non-owner, the readability wall must run BEFORE the "already resolved" InvalidOperation, or resolved-state remains an oracle over withheld rows — a withheld row must yield the identical NotFound whether open or resolved; owner keeps today's behavior exactly (item-less dismiss, existing messages, test_review_auto.py:109-125 unchanged). Keep require_cap(CAP_REVIEW_RESOLVE) at the surface layers per the composition contract (scope.py:348-359 — it is per-principal-constant so it may precede row walls); adding it inside dismiss too is acceptable defense-in-depth but is NOT a substitute for the project walls. The web route maps NotFound → the zone's byte-identical 404 and InvalidOperation → the uniform write-rejection rendering shared with /item/{id}/supersede. Pin with tests: (1) grantee rw-on-A dismissing a project-B row gets a NotFound whose message is string-equal to the missing-row message; (2) same for an item-less sentinel row and for a RESOLVED withheld row; (3) read-only grantee on A gets the uniform _not_writable message only after readability passes; (4) bulk_resolve('dismiss') under a grantee principal inherits the walls as per-row errors with no cross-project flips; (5) the confined-write-allowlist test asserts views_write imports dismiss only from kbcore.review (never re-implements the query). Also note in the review record: resolve_review (review.py:77-84, unconditional UPDATE, no existence check) has the same kbcore-level hole — it is not in the proposed web import set, so the allowlist test must keep it out, and any future exposure requires the same treatment.

### [2] CRITICAL — must-fix-prerequisite — kbcore review promote/reject/dismiss carry NO require_cap; the coarse /review zone wall cannot separate READ from RESOLVE
**File:** `src/kbcore/review.py`  
**Attack:** A principal granted CAP_REVIEW_READ (list access) plus an rw grant on project P — but deliberately NOT CAP_REVIEW_RESOLVE — POSTs /review/{qid}/resolve for a P-scoped queue row. The zone wall admits them (they have the read cap); kbcore.review.promote never checks CAP_REVIEW_RESOLVE; assert_writable(P) passes (they have rw). Result: an under-capped principal performs the unverified→verified TRUST ESCALATION from the internet-facing surface.  
**Required mitigation:** Four-part prerequisite, sharpened from the proposal: (1) ROUTE-LEVEL: map the /review zone to CAP_REVIEW_READ and have the /review/{qid}/resolve view call scope.require_cap(scope.CAP_REVIEW_RESOLVE) BEFORE any kbcore call, following the shipped defense-in-depth pattern _cap_or_404 (views_export.py:53-62) including its unset-principal RuntimeError branch; the under-capped response must be the byte-identical unknown-path 404, NOT require_cap's InvalidOperation text surfaced as a 4xx (require_cap's message differs from the zone wall's bytes — the web layer must translate). (2) KBCORE BACKSTOP: add scope.require_cap(CAP_REVIEW_RESOLVE) at the top of promote, reject, dismiss, resolve_via_supersede, and apply_suggestion — placed BEFORE _queued_item_id, which is oracle-safe because require_cap is per-principal-constant and target-independent (scope.py:348-358). Proven non-breaking: CLI/worker run as implicit OWNER (scope.py:153-167) and OWNER short-circuits has_cap; MCP's require_owner remains strictly stronger. (3) DISMISS-SPECIFIC (the finding missed this): dismiss (review.py:212-234) today has NEITHER row wall NOR cap and leaks 'does not exist' vs 'already resolved' — before it is web-reachable it must gate item-bearing rows through _queued_item_id-style readability (collapsing the not-readable case to the same NotFound) and restrict item-less-row dismissal to owner, or a web resolve with action=dismiss becomes both an unauthorized queue-drain primitive and an existence oracle for withheld-project queue rows. (4) TEST PINS: (a) construct Principal(caps=frozenset({CAP_REVIEW_READ})) directly (no ROLE_CAPS bundle produces it — that is the point) and assert POST /review/{qid}/resolve returns bytes identical to the router's unknown-path 404; (b) assert kbcore.review.promote/reject/dismiss raise under that principal (the backstop test); (c) a ROLE_CAPS drift-pin asserting no bundle other than reviewer ever contains CAP_REVIEW_RESOLVE, so a future bundle edit cannot silently widen the trust-escalation surface.

### [3] CRITICAL — design-flaw — Web-reachable promote creates a self-verification laundering loop (save-unverified -> resolve-promote -> verified, all from the internet surface)
**File:** `src/kbcore/review.py:187`  
**Attack:** One principal with role=reviewer and an rw grant on project X: (1) POST /save {project:X, type:decision, ...} -> forced trust='unverified' + review_queue row; (2) POST /review/{qid}/resolve action=promote -> _queued_item_id passes (X readable+writable) -> sources.trust='verified'. Forged item now outranks and out-canonicalizes real knowledge and is no longer review-flagged.  
**Required mitigation:** Make the exclusion categorical AND mechanically pinned, and extend it to dismiss:

(a) Do NOT import review.promote into kbweb/views_write.py. Change the proposed confined-write allowlist from {ingest, supersede, link, promote, reject, dismiss} to {ingest, supersede, link, reject}. Trust escalation (unverified→verified) stays owner-only via CLI/MCP require_owner (tools_phase5.py:103/123/157) — it is never reachable from an authenticated non-owner web request.

(b) Also drop `dismiss` from the web /review/{qid}/resolve action set. dismiss (review.py:212-234) does not escalate trust, but it flips resolved=true while leaving the item trust='unverified' and RETRIEVABLE — so a web saver could silently de-flag their own forged item so no human ever reviews it, converting the review-bounded injection window into a permanent one. The only defensible non-owner web resolve action is `reject` (review.py:200-209), which archives the item (Invariant-5 status flip) and thus also removes it from retrieval; even that should be gated behind CAP_REVIEW_RESOLVE + an rw grant and flagged for the separate reject-griefing consideration (a web reviewer can archive co-contributors' legitimate unverified items in a shared rw project).

(c) Enforce the exclusion as an invariant, not a convention: rewrite the current zero-write-import trip-wire in tests/test_web_caps.py into a confined-write-ALLOWLIST test that pins views_write.py's imported symbols to exactly {ingest, supersede, link, reject} and asserts `promote` and `dismiss` are NOT imported — so any future re-addition of a trust-escalation path to the web surface fails CI mechanically.

This is strictly stronger than a same-author self-promote guard: it survives grantee collusion, needs no item-authorship column (which does not exist, 001_init.sql:27-43), and keeps the internet-facing surface incapable of reaching the 'verified' tier at all.

### [4] CRITICAL — design-flaw — /item/{id}/supersede mints a trust='verified' item directly, bypassing the forced-unverified rule with no review row at all
**File:** `src/kbcore/supersede.py:93`  
**Attack:** POST /item/{verified_owner_item}/supersede {new_body:'<forged correction>', reason:'...'} with an rw grant on that project -> supersede.py:93 ingest_in trust='verified' -> a verified web-authored item becomes active; the owner's item is superseded. Entirely from the web, no review touched.  
**Required mitigation:** Fix in kbcore at the single write point, not in route wrappers — the current API makes route-level compliance impossible (supersede() exposes no trust parameter). (1) In ingest_in, immediately after require_cap/assert_writable (ingest.py:175-178), coerce: if not scope.current().is_owner, force trust='unverified' regardless of the caller-passed value. This automatically covers /save, the supersede new_body path, and any future composed write — and closes the SAME pre-existing hole in MCP kb_supersede (kbmcp/server.py:343), which today lets any rw token principal mint verified items. (2) In supersede(), when scope.current() is non-owner, queue_review_in(conn, new_item_id, 'unverified_extraction'|'proposed_supersession', ...) in the SAME transaction, preserving the crash-safety property _ingest_and_queue documents (kbworker/sessions.py:241-245). (3) Gate the TARGET: supersede currently never reads the old item's source trust (its SELECT at supersede.py:51-57 omits it — add a sources join); for non-owner principals, refuse to supersede an item whose source trust='verified', because the status flip alone is a retrieval-suppression primitive (search.py:120 drops superseded items) independent of the minted trust. Error must reuse the existing writability-rejection shape so no verified/unverified oracle opens. (4) Stronger alternative worth mandating for the web surface: non-owner web supersede does not call supersede() at all — it enqueues a 'proposed_supersession' review row carrying {old_id, new_body, reason}, and the owner's promote performs the actual supersede; this keeps the destructive-visibility status flip owner-mediated entirely. (5) Regression tests: with a non-owner rw principal bound via use_principal, (a) ingest_in(trust='verified') must persist sources.trust='unverified'; (b) supersede(new_body=...) must yield an unverified source plus a review row in one transaction, or raise when the target is verified; (c) owner path unchanged.

### [5] CRITICAL — design-flaw — supersede() new_body path mints trust='verified' with NO review row — a CSRF-correct, capped web write bypasses the 'forced unverified + queue' premise
**File:** `src/kbcore/supersede.py:86-98`  
**Attack:** Log in as a live 'contributor' grantee with an rw grant on project P. GET /item/{id} (an item in P) to obtain a same-identity CSRF token. POST /item/{id}/supersede with new_body='<injected decision text>' and that csrf value. supersede() runs ingest_in(trust='verified'), producing a verified item in P with no review_queue row; kb_search now returns it as trusted knowledge to agents.  
**Required mitigation:** Three-part fix, strongest first. (A) STRUCTURAL (fixes web AND the live MCP hole at kbmcp/server.py:217): enforce trust policy at the single write point — in ingest_in (src/kbcore/ingest.py), immediately after require_cap/assert_writable (~:175-178), force trust="unverified" whenever scope.current().is_owner is False. No surface (web, MCP, future) can then mint verified as a non-owner, mirroring how require_cap/assert_writable already live in kbcore rather than per-surface. (B) CONFINED ENTRY POINT: do not route the web to raw ingest/supersede. Add one kbcore function (e.g. kbcore.web_write.save_for_review) that composes ingest_in(trust="unverified") + queue_review_in(conn, item_id, "unverified_extraction"|new reason "web_contribution", detail) inside ONE transaction() — lifting kbworker.sessions._ingest_and_queue (sessions.py:246-262, whose docstring already states the crash-atomicity requirement) into kbcore — and make the allowlist {save_for_review, link, promote, reject, dismiss}. (C) SUPERSEDE MUST BE A PROPOSAL, NOT AN ACT: forcing unverified on the new_body path is NOT sufficient — supersede.py:133-141 flips the old (verified) item to status='superseded' regardless of replacement trust, so even an unverified+queued replacement immediately suppresses genuine verified knowledge from active search until review. Non-owner web supersede must therefore either (i) be restricted to a review-queue proposal: ingest the replacement unverified+queued with a 'proposed_supersede' detail linking old_id, applying the actual status flip only at promote time via review.resolve_via_supersede (review.py:237), or (ii) be dropped from Branch B scope. TESTS: (1) with a non-owner principal bound, exercise every kbweb mutating route and assert no sources row with trust='verified' is ever created and every created item has exactly one open review_queue row; (2) crash-atomicity: monkeypatch queue_review_in to raise and assert the item insert rolled back; (3) assert no non-owner path changes any pre-existing item's status before a promote; (4) extend the tests/test_web_caps.py allowlist test so ingest/supersede (raw) importing into kbweb fails closed.

### [6] CRITICAL — must-fix-prerequisite — Web-saved unverified content is immediately retrievable by kb_search — an indirect prompt-injection channel into every agent session until reviewed

### [12] HIGH — design-flaw — resolve action set must be reject/dismiss only, and reject must be confined to unverified targets (reject of a verified item is web-reachable knowledge suppression)
**File:** `src/kbcore/review.py:200`  
**Attack:** A contradiction review row references a verified owner item in project X. Reviewer with rw on X: POST /review/{qid}/resolve action=reject -> item archived, dropped from active search, while the reviewer's competing unverified item remains.  
**Required mitigation:** Web non-owner resolve set = {dismiss, reject}, with BOTH primitives hardened in kbcore (not the web layer, so any future grantee MCP surface inherits the invariant): (a) In reject(), after _queued_item_id resolves the item, when not scope.current().is_owner require the item's joined source trust to be literally 'unverified' (NULL source counts as verified/protected, matching the item_ranks convention at consolidation.py:137); otherwise raise InvalidOperation — archiving verified knowledge stays owner/CLI-only. (b) dismiss() must gain the same readable-then-writable resolution as _queued_item_id for non-owners (readability FIRST, reusing the byte-identical 'review queue row {id} does not exist' NotFound so a withheld-project row is indistinguishable from a missing one — including the already-resolved case, which currently oracles existence); item-less rows (search_regression sentinel) are owner-only since there is no project to scope them to.
